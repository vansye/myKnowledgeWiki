## 为什么需要全局异常处理

在 Web 开发中，程序运行时难免会出现各种异常：

- 用户输入了非法数据
- 数据库连接失败
- 业务逻辑校验不通过
- 空指针异常
- ...

如果没有统一处理，这些异常会直接暴露给前端，用户体验差，也不安全。

### 生活中的类比

想象一家餐厅：

- **没有全局异常处理**：厨师做菜失败了，直接把烧焦的菜端给顾客，顾客看到后很困惑
- **有全局异常处理**：厨师做菜失败了，服务员统一回复"抱歉，这道菜暂时无法提供"，并记录问题

全局异常处理就是那个**统一回复的服务员**。

## 没有全局异常处理的问题

### 问题 1：异常信息直接暴露

```json
// 没有全局异常处理时，前端收到的响应
{
    "timestamp": "2026-07-22T10:30:00",
    "status": 500,
    "error": "Internal Server Error",
    "message": "java.lang.NullPointerException: Cannot invoke method on null object",
    "path": "/emps/1"
}
```

**问题：**

- 暴露了技术细节（类名、方法名、堆栈信息）
- 用户看不懂
- 有安全风险（攻击者可以利用这些信息）

### 问题 2：每个方法都要写 try-catch

```java
// 没有全局异常处理，每个方法都要重复写
@GetMapping("/emps/{id}")
public Result getById(@PathVariable Integer id) {
    try {
        Emp emp = empService.getById(id);
        return Result.success(emp);
    } catch (Exception e) {
        return Result.error("查询失败：" + e.getMessage());
    }
}

@DeleteMapping("/emps/{id}")
public Result delete(@PathVariable Integer id) {
    try {
        empService.delete(id);
        return Result.success();
    } catch (Exception e) {
        return Result.error("删除失败：" + e.getMessage());
    }
}
// ... 每个方法都要写一遍
```

**问题：**

- 代码冗余，大量重复的 try-catch
- 业务逻辑被异常处理代码淹没
- 维护困难

## 全局异常处理的核心注解

| 注解 | 作用 |
|------|------|
| `@RestControllerAdvice` | 标记全局异常处理类（`@ControllerAdvice` + `@ResponseBody`） |
| `@ExceptionHandler` | 指定处理的异常类型 |
| `@ResponseStatus` | 设置 HTTP 响应状态码 |

### `@RestControllerAdvice` vs `@ControllerAdvice`

```java
// @ControllerAdvice：返回视图
@ControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(Exception.class)
    public String handleException(Exception e) {
        return "error";  // 返回视图名
    }
}

// @RestControllerAdvice：返回 JSON（推荐，前后端分离项目）
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(Exception.class)
    public Result handleException(Exception e) {
        return Result.error(e.getMessage());  // 返回 JSON
    }
}
```

## 实现全局异常处理

### 完整示例

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    /**
     * 处理所有异常（兜底）
     */
    @ExceptionHandler(Exception.class)
    public Result handleException(Exception e) {
        // 记录日志
        log.error("系统异常：", e);
        return Result.error("系统繁忙，请稍后重试");
    }

    /**
     * 处理业务异常
     */
    @ExceptionHandler(BusinessException.class)
    public Result handleBusinessException(BusinessException e) {
        log.warn("业务异常：{}", e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    /**
     * 处理参数校验异常
     */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result handleValidException(MethodArgumentNotValidException e) {
        // 获取第一个校验错误的信息
        String message = e.getBindingResult().getFieldErrors().get(0).getDefaultMessage();
        return Result.error(message);
    }

    /**
     * 处理类型转换异常
     */
    @ExceptionHandler(HttpMessageNotReadableException.class)
    public Result handleMessageException(HttpMessageNotReadableException e) {
        return Result.error("请求参数格式错误");
    }
}
```

### 执行流程

```
Controller 方法抛出异常
        │
        ▼
SpringMVC 查找 @RestControllerAdvice 类
        │
        ▼
匹配 @ExceptionHandler 的异常类型
        │
        ├── 找到匹配的 → 执行对应处理方法 → 返回统一响应
        │
        └── 没找到 → 向上找父类异常的处理器
                    │
                    └── 最终没找到 → 返回默认错误页面
```

### 要点

- **从具体到通用**：先写具体异常的处理，最后写 `Exception.class` 兜底
- **记录日志**：异常处理中一定要记录日志，方便排查问题
- **返回统一格式**：所有异常都返回 `Result` 对象，前端统一处理

## 自定义业务异常

### 为什么要自定义异常

系统异常（如空指针、数据库异常）和业务异常（如"用户名已存在"、"部门不存在"）应该区别对待：

- 系统异常：返回通用提示"系统繁忙"
- 业务异常：返回具体的业务提示信息

### 定义业务异常类

```java
/**
 * 自定义业务异常
 */
public class BusinessException extends RuntimeException {

    private Integer code;  // 业务错误码

    public BusinessException(String message) {
        super(message);
        this.code = 0;
    }

    public BusinessException(Integer code, String message) {
        super(message);
        this.code = code;
    }

    public Integer getCode() {
        return code;
    }
}
```

### 在业务层抛出

```java
@Service
public class EmpService {

    public void delete(Long id) {
        // 检查员工是否存在
        Emp emp = empMapper.findById(id);
        if (emp == null) {
            throw new BusinessException("员工不存在");
        }

        // 检查员工是否有关联部门
        if (emp.getDeptId() != null) {
            throw new BusinessException(1001, "该员工有关联部门，无法删除");
        }

        empMapper.deleteById(id);
    }
}
```

### 在全局异常处理中捕获

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public Result handleBusinessException(BusinessException e) {
        // 业务异常：返回具体的业务提示信息
        return Result.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public Result handleException(Exception e) {
        // 系统异常：返回通用提示
        log.error("系统异常：", e);
        return Result.error("系统繁忙，请稍后重试");
    }
}
```

### 效果对比

```java
// 没有自定义异常
if (emp == null) {
    return Result.error("员工不存在");  // 每个地方都要写
}

// 有自定义异常
if (emp == null) {
    throw new BusinessException("员工不存在");  // 抛出即可，全局统一处理
}
```

## 异常处理的最佳实践

### 1. 异常分类处理

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 业务异常 → 返回具体提示
    @ExceptionHandler(BusinessException.class)
    public Result handleBusiness(BusinessException e) { ... }

    // 参数校验异常 → 返回校验信息
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result handleValid(MethodArgumentNotValidException e) { ... }

    // 认证异常 → 返回 401
    @ExceptionHandler(AuthenticationException.class)
    public Result handleAuth(AuthenticationException e) { ... }

    // 所有其他异常 → 兜底
    @ExceptionHandler(Exception.class)
    public Result handleAll(Exception e) { ... }
}
```

### 2. 异常处理顺序

**从具体到通用**，Spring 会匹配最具体的异常处理器：

```
BusinessException（最具体）
    ↑ 继承
RuntimeException
    ↑ 继承
Exception（最通用，兜底）
```

### 3. 日志记录

```java
@ExceptionHandler(Exception.class)
public Result handleException(Exception e) {
    // 记录完整堆栈信息，方便排查
    log.error("系统异常，请求路径：{}", request.getRequestURI(), e);
    return Result.error("系统繁忙，请稍后重试");
}
```

### 4. 不要吞掉异常

```java
// 错误做法：吞掉异常，不记录日志
@ExceptionHandler(Exception.class)
public Result handleException(Exception e) {
    return Result.error("出错了");  // 不知道发生了什么
}

// 正确做法：记录日志后再返回
@ExceptionHandler(Exception.class)
public Result handleException(Exception e) {
    log.error("系统异常：", e);  // 记录日志
    return Result.error("系统繁忙，请稍后重试");
}
```

## 常见问题与解决方案

### 问题 1：全局异常处理不生效

**原因：**

- 异常处理类没有被 Spring 扫描到
- 异常被 Controller 方法内部的 try-catch 捕获了

**解决方案：**

- 确保异常处理类在 Spring 的包扫描范围内
- Controller 方法中不要捕获异常，让异常抛出去

### 问题 2：多个异常处理器匹配冲突

**原因：**

定义了多个能处理同一异常的处理器。

**解决方案：**

- 确保异常类型不重复
- 从具体到通用排列

### 问题 3：异步方法中的异常无法捕获

**原因：**

`@Async` 注解的方法在另一个线程执行，异常不会传播到 Controller。

**解决方案：**

- 在异步方法内部处理异常
- 使用 `AsyncUncaughtExceptionHandler`

## 小结

### 核心要点

| 要点 | 说明 |
|------|------|
| **`@RestControllerAdvice`** | 标记全局异常处理类 |
| **`@ExceptionHandler`** | 指定处理的异常类型 |
| **自定义业务异常** | 区分业务异常和系统异常 |
| **从具体到通用** | 先处理具体异常，最后用 Exception 兜底 |
| **记录日志** | 异常处理中一定要记录日志 |
| **统一响应格式** | 所有异常都返回 Result 对象 |

### 口诀

**异常处理要全局，RestControllerAdvice 来标记；  
ExceptionHandler 分类型，业务系统要区分；  
从具体到通用排，日志记录不能少；  
统一格式返回去，前端处理没烦恼。**

### 最容易混淆的两个点

- **`@ControllerAdvice` vs `@RestControllerAdvice`**：前者返回视图，后者返回 JSON（前后端分离用后者）
- **业务异常 vs 系统异常**：业务异常返回具体提示（如"用户名已存在"），系统异常返回通用提示（如"系统繁忙"）

---

全局异常处理的本质是：**把分散在各个方法中的异常处理逻辑集中到一个地方，统一捕获、统一记录、统一返回，让代码更干净，让用户体验更好。**
