## 什么是事务

**事务（Transaction）** 是一组数据库操作，它们要么**全部成功**，要么**全部失败**，不会出现部分成功部分失败的情况。

### 生活中的类比

**银行转账**是最经典的事务场景：

```
张三给李四转账 100 元：

步骤1：张三的账户 -100 元
步骤2：李四的账户 +100 元
```

- **有事务**：步骤1和步骤2要么都成功，要么都失败
  - 如果步骤2失败（如李四账户不存在），步骤1也会回滚，张三的钱不会少
- **没有事务**：步骤1成功了，步骤2失败了
  - 张三的钱少了100，但李四没收到 → 钱凭空消失了！

## 为什么需要事务

### 没有事务的问题

```java
// 没有事务：两步操作独立执行
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    // 步骤1：扣款
    accountMapper.deduct(fromId, amount);  // 成功了

    // 步骤2：加款（如果这里失败了）
    int result = 1 / 0;  // 异常！
    accountMapper.add(toId, amount);  // 不会执行
}
// 结果：fromId 扣了钱，toId 没收到 → 数据不一致！
```

### 有事务的保障

```java
// 有事务：两步操作要么都成功，要么都失败
@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    accountMapper.deduct(fromId, amount);  // 步骤1
    accountMapper.add(toId, amount);       // 步骤2
    // 如果步骤2失败，步骤1也会回滚
}
```

## 事务的四大特性（ACID）

| 特性 | 英文 | 说明 | 示例 |
|------|------|------|------|
| **原子性** | Atomicity | 事务中的操作要么全部成功，要么全部失败 | 转账的两步操作不可分割 |
| **一致性** | Consistency | 事务执行前后，数据保持一致性 | 转账前后总金额不变 |
| **隔离性** | Isolation | 多个事务之间互不干扰 | A 转账时 B 不能看到中间状态 |
| **持久性** | Durability | 事务提交后，数据永久保存 | 提交后即使断电数据也不丢失 |

### 用转账理解 ACID

```
张三(1000元) → 李四(500元)，转账100元

原子性：扣款和加款要么都成功，要么都失败
一致性：转账前 1000+500=1500，转账后 900+600=1500，总额不变
隔离性：转账过程中，其他人看不到"张三已扣款但李四未加款"的中间状态
持久性：转账成功后，即使数据库重启，数据也不会丢失
```

## Spring 事务管理

Spring 提供了两种事务管理方式，声明式事务的底层基于 [[SpringAOP技术]] 实现：

| 方式 | 说明 | 使用频率 |
|------|------|----------|
| **声明式事务** | 用 `@Transactional` 注解，简单方便 | **常用** |
| **编程式事务** | 用代码手动控制事务，灵活但繁琐 | 少用 |

### 声明式事务（推荐）

只需要在方法上加 `@Transactional` 注解，Spring 自动管理事务。

```java
@Service
public class EmpService {

    @Transactional  // 开启事务
    public void deleteDept(Long id) {
        // 步骤1：删除部门下的员工
        empMapper.deleteByDeptId(id);

        // 步骤2：删除部门
        deptMapper.deleteById(id);

        // 如果步骤2失败，步骤1也会回滚
    }
}
```

**要点：**

- `@Transactional` 加在 Service 层的方法上
- 默认遇到 RuntimeException 和 Error 时回滚
- 默认遇到 Checked Exception 时不回滚

---

## `@Transactional` 注解详解

### 常用属性

```java
@Transactional(
    rollbackFor = Exception.class,       // 指定哪些异常触发回滚
    noRollbackFor = BusinessException.class,  // 指定哪些异常不回滚
    timeout = 30,                         // 超时时间（秒）
    readOnly = false,                     // 是否只读
    propagation = Propagation.REQUIRED,   // 传播行为
    isolation = Isolation.READ_COMMITTED  // 隔离级别
)
public void someMethod() {
    // ...
}
```

### 属性说明

| 属性 | 说明 | 默认值 |
|------|------|--------|
| `rollbackFor` | 指定哪些异常触发回滚 | RuntimeException + Error |
| `noRollbackFor` | 指定哪些异常不回滚 | 无 |
| `timeout` | 事务超时时间（秒） | -1（不超时） |
| `readOnly` | 是否只读事务 | false |
| `propagation` | 传播行为 | REQUIRED |
| `isolation` | 隔离级别 | 数据库默认 |

### `rollbackFor` 的重要性

```java
// 默认情况：只回滚 RuntimeException 和 Error
@Transactional
public void method1() {
    // 抛出 IOException（Checked Exception）→ 不会回滚！
    throw new IOException("文件读取失败");
}

// 指定 rollbackFor：所有异常都回滚
@Transactional(rollbackFor = Exception.class)
public void method2() {
    // 抛出任何 Exception → 都会回滚
    throw new IOException("文件读取失败");
}
```

**最佳实践：** 总是加上 `rollbackFor = Exception.class`

```java
@Transactional(rollbackFor = Exception.class)
public void deleteDept(Long id) {
    // ...
}
```

## 事务的传播行为

**传播行为**决定了：当一个事务方法调用另一个事务方法时，事务如何传播。

### 常见传播行为

| 传播行为 | 含义 | 使用场景 |
|----------|------|----------|
| `REQUIRED`（默认） | 有事务就加入，没有就新建 | 大多数场景 |
| `REQUIRES_NEW` | 总是新建事务，挂起当前事务 | 日志记录（不管主事务是否成功都要记录） |
| `NESTED` | 嵌套事务，外层回滚内层也回滚，内层回滚不影响外层 | 部分操作可独立回滚 |
| `SUPPORTS` | 有事务就加入，没有就不使用事务 | 查询操作 |
| `NOT_SUPPORTED` | 不使用事务 | 非数据库操作 |
| `MANDATORY` | 必须在事务中运行，否则报错 | 强制要求事务 |
| `NEVER` | 不能在事务中运行 | 强制要求无事务 |

### `REQUIRED`（默认）

```java
@Transactional  // 事务 A
public void methodA() {
    // 操作1
    methodB();  // 调用 methodB，加入事务 A
}

@Transactional  // 事务 B（传播行为默认 REQUIRED）
public void methodB() {
    // 操作2
}
// methodA 和 methodB 在同一个事务中，任何一个失败都回滚
```

### `REQUIRES_NEW`

```java
@Transactional  // 事务 A
public void methodA() {
    // 操作1
    methodB();  // methodB 会新建一个独立的事务
    // 操作3（如果这里失败，事务 A 回滚，但 methodB 的事务已经提交了）
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void methodB() {
    // 操作2（独立事务，不受事务 A 影响）
}
```

**典型场景：** 记录操作日志

```java
@Transactional(rollbackFor = Exception.class)
public void deleteDept(Long id) {
    // 删除部门
    deptMapper.deleteById(id);

    // 记录日志（即使删除失败，日志也要保存）
    logService.saveLog("删除部门：" + id);
}

@Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
public void saveLog(String content) {
    logMapper.insert(content);  // 独立事务，不受外层影响
}
```

## 事务的隔离级别

**隔离级别**决定了：多个事务同时操作同一数据时，如何保证数据的一致性。

### 并发问题

| 问题 | 说明 | 示例 |
|------|------|------|
| **脏读** | 读到了其他事务未提交的数据 | A 修改数据但未提交，B 读到了修改后的数据，A 回滚后 B 读到的是脏数据 |
| **不可重复读** | 同一事务内两次读取结果不同 | A 第一次读到数据，B 修改并提交了数据，A 第二次读到的是修改后的数据 |
| **幻读** | 同一事务内两次查询的记录数不同 | A 第一次查到10条记录，B 插入了一条记录并提交，A 第二次查到11条 |

### 隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|----------|------|-----------|------|------|
| `READ_UNCOMMITTED` | 可能 | 可能 | 可能 | 最高 |
| `READ_COMMITTED` | 不会 | 可能 | 可能 | 较高 |
| `REPEATABLE_READ`（MySQL 默认） | 不会 | 不会 | 可能（MySQL 已解决） | 较低 |
| `SERIALIZABLE` | 不会 | 不会 | 不会 | 最低 |

### 在 Spring 中设置

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public void method() {
    // ...
}
```

**建议：** 一般情况下使用数据库默认的隔离级别即可，不需要手动设置。

## 事务失效的常见场景

### 场景 1：方法不是 public 的

```java
// 错误：@Transactional 对非 public 方法无效
@Transactional
private void deleteDept(Long id) {  // private，事务不生效！
    // ...
}

// 正确
@Transactional
public void deleteDept(Long id) {  // public，事务生效
    // ...
}
```

### 场景 2：同类内部方法调用

```java
@Service
public class EmpService {

    public void methodA() {
        // 调用同类的方法 → 绕过了 Spring 代理 → 事务不生效！
        this.methodB();
    }

    @Transactional
    public void methodB() {  // 事务不生效
        // ...
    }
}
```

**原因：** Spring 事务基于 AOP 代理实现，同类内部调用不会经过代理对象。

**解决方案：**

```java
// 方案一：注入自己
@Service
public class EmpService {

    @Autowired
    private EmpService self;  // 注入代理对象

    public void methodA() {
        self.methodB();  // 通过代理对象调用，事务生效
    }

    @Transactional
    public void methodB() {
        // ...
    }
}

// 方案二：拆分到不同的 Service 中
@Service
public class EmpServiceA {
    @Autowired
    private EmpServiceB serviceB;

    public void methodA() {
        serviceB.methodB();  // 跨类调用，事务生效
    }
}

@Service
public class EmpServiceB {
    @Transactional
    public void methodB() {
        // ...
    }
}
```

### 场景 3：异常被 catch 了没有抛出

```java
@Transactional
public void deleteDept(Long id) {
    try {
        deptMapper.deleteById(id);
        int result = 1 / 0;  // 异常
    } catch (Exception e) {
        // 异常被吞掉了，事务不会回滚！
        log.error("删除失败", e);
    }
}
```

**解决方案：**

```java
@Transactional
public void deleteDept(Long id) {
    try {
        deptMapper.deleteById(id);
        int result = 1 / 0;
    } catch (Exception e) {
        log.error("删除失败", e);
        throw e;  // 重新抛出异常，触发回滚
    }
}
```

### 场景 4：数据库引擎不支持事务

```sql
-- MyISAM 引擎不支持事务
CREATE TABLE emp (...) ENGINE=MyISAM;

-- InnoDB 引擎支持事务
CREATE TABLE emp (...) ENGINE=InnoDB;
```

### 场景 5：没有加 `rollbackFor`

```java
// 默认只回滚 RuntimeException，Checked Exception 不会回滚
@Transactional
public void method() throws IOException {
    throw new IOException("文件操作失败");  // 不会回滚！
}

// 加上 rollbackFor
@Transactional(rollbackFor = Exception.class)
public void method() throws IOException {
    throw new IOException("文件操作失败");  // 会回滚
}
```

## 编程式事务 vs 声明式事务

### 声明式事务（推荐）

```java
@Transactional
public void deleteDept(Long id) {
    // 代码简洁，Spring 自动管理事务
}
```

### 编程式事务（了解）

```java
@Autowired
private TransactionTemplate transactionTemplate;

public void deleteDept(Long id) {
    transactionTemplate.execute(status -> {
        try {
            empMapper.deleteByDeptId(id);
            deptMapper.deleteById(id);
            return null;
        } catch (Exception e) {
            status.setRollbackOnly();  // 手动回滚
            throw e;
        }
    });
}
```

**对比：**

| 特性 | 声明式事务 | 编程式事务 |
|------|-----------|-----------|
| 写法 | 注解，简单 | 代码，繁琐 |
| 灵活性 | 一般 | 高（可以精确控制回滚点） |
| 使用频率 | **常用** | 少用 |
| 适用场景 | 大多数场景 | 需要精细控制事务的场景 |

## 常见问题与解决方案

### 问题 1：事务不生效

**排查清单：**

- [ ] 方法是否是 public 的
- [ ] 是否是同类内部调用
- [ ] 异常是否被 catch 后没有抛出
- [ ] 是否加了 `rollbackFor = Exception.class`
- [ ] 数据库引擎是否支持事务（InnoDB）
- [ ] 类是否被 Spring 管理（有 `@Service` 注解）

### 问题 2：事务超时

**原因：**

事务执行时间超过了设置的超时时间。

**解决方案：**

```java
// 增加超时时间
@Transactional(timeout = 60)  // 60 秒
public void longMethod() {
    // ...
}
```

### 问题 3：死锁

**原因：**

多个事务以不同的顺序锁定相同的资源。

**解决方案：**

- 确保多个事务以相同的顺序访问资源
- 减少事务的持有时间
- 使用较低的隔离级别

## 小结

### 核心要点

| 要点 | 说明 |
|------|------|
| **事务** | 一组操作要么全部成功，要么全部失败 |
| **ACID** | 原子性、一致性、隔离性、持久性 |
| **`@Transactional`** | 声明式事务，加在 Service 方法上 |
| **`rollbackFor`** | 指定回滚的异常类型，建议加 `Exception.class` |
| **传播行为** | REQUIRED（默认，加入当前事务）、REQUIRES_NEW（新建独立事务） |
| **隔离级别** | 一般用数据库默认即可 |
| **事务失效** | 非 public、同类调用、异常被吞、引擎不支持 |

### 口诀

**事务保证一致性，ACID 四特性；  
Transactional 加方法，rollbackFor 别忘记；  
REQUIRED 是默认，REQUIRES_NEW 建独立；  
同类调用会失效，异常吞掉不回滚。**

### 最容易混淆的三个点

- **`REQUIRED` vs `REQUIRES_NEW`**：前者加入当前事务（一起回滚），后者新建独立事务（互不影响）
- **声明式 vs 编程式**：声明式用注解（简单），编程式用代码（灵活）
- **脏读 vs 不可重复读 vs 幻读**：脏读是读未提交数据，不可重复读是两次读结果不同，幻读是两次查询记录数不同

---

事务管理的本质是：**保证一组数据库操作的原子性，要么全部成功，要么全部失败，确保数据的一致性。**

掌握事务管理，你就能写出数据安全的业务代码！
